# API Conventions

This steering file is the single source of truth, at steering level, for the EDU-IT HTTP API
conventions. It is included conditionally when working on API code (see the `fileMatchPattern`
in the front matter), which is the `apps/api` FastAPI boundary. The conventions below mirror the
companion design document `docs/API-CONVENTIONS.md` (D2); all numbers and normative wording are
preserved unchanged. This steering file (S12) is produced after D2 is complete, per Requirements
1.8 and 1.9. When D2 and this file could ever disagree, D2 is the authoritative source.

The API is the `apps/api` FastAPI boundary. It validates requests and responses with Pydantic v2
and is the only component exposed to the learner and reviewer browsers (the Next.js `apps/web`
app calls it through a generated OpenAPI client, and learners attach the authenticated terminal
WebSocket to it).

Learner-facing errors are translated (French/English) and actionable; diagnostic details stay in
logs rather than in responses. The authoritative quality and testing rules live in steering:
#[[file:.kiro/steering/quality.md]].

_Companion design document:_ `docs/API-CONVENTIONS.md` (D2). Failure scenario 4.6 is also
documented at the data level in `docs/DATA-MODEL.md` (D3); the domain rule it encodes is in
#[[file:.kiro/steering/domain-rules.md]].

## 1. Error Format — RFC 9457 Problem Details

All error responses use [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) problem details. The
response body is a JSON object served with the `application/problem+json` media type and carries
the five standard problem-details members:

| Member     | Type    | Description |
|------------|---------|-------------|
| `type`     | string (URI) | A URI reference that identifies the problem type. Dereferencing it SHOULD provide human-readable documentation for the problem type. When no specific type applies, the value is `"about:blank"`. |
| `title`    | string  | A short, human-readable summary of the problem type. It does not change from occurrence to occurrence of the problem (aside from localization). |
| `status`   | number  | The HTTP status code generated by the origin server for this occurrence of the problem. It matches the response's actual HTTP status code. |
| `detail`   | string  | A human-readable explanation specific to this occurrence of the problem. Learner-facing `detail` text is translated and actionable; sensitive diagnostic details stay in logs, not in `detail`. |
| `instance` | string (URI) | A URI reference that identifies the specific occurrence of the problem. |

### Rules

- Every non-2xx response is a problem-details document containing at least `type`, `title`, and
  `status`. `detail` and `instance` are included whenever they add value for the caller.
- `status` in the body always equals the HTTP response status code.
- `title` is stable per problem type; occurrence-specific information goes in `detail`.
- Learner-facing `detail` strings are translated to the request locale (French/English) and are
  actionable. Internal diagnostics (stack traces, SQL, provider errors) are never placed in the
  response; they are written to logs (#[[file:.kiro/steering/quality.md]]).
- Validation failures (Pydantic v2) are returned as problem details; field-level errors are
  reported in a problem extension member without leaking internal representations.

### Example

```http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{
  "type": "https://api.edu-it.example/problems/duplicate-submission",
  "title": "Duplicate submission",
  "status": 409,
  "detail": "This quiz submission was already received and processed.",
  "instance": "/v1/quiz-attempts/qa_01HZX9Q0K8"
}
```

Problem documents MAY carry additional extension members (for example a `pagination` echo or a
`fields` array for validation errors). Extension members never redefine the five standard
members above.

## 2. Pagination Strategy

List endpoints use **cursor-based (keyset) pagination**. A cursor is an opaque, URL-safe token
that encodes the position of the last item returned; clients treat it as opaque and never parse
it.

### Request parameters

| Parameter | Type   | Description |
|-----------|--------|-------------|
| `limit`   | number | Maximum number of items to return in one page. The server applies a default and a maximum; requests above the maximum are clamped to the maximum. |
| `cursor`  | string | Opaque token returned by a previous response as `next_cursor`. Omitted on the first request. |

### Response shape

```json
{
  "data": [ /* items */ ],
  "page": {
    "next_cursor": "eyJpZCI6ImNrXzAxSFoifQ",
    "has_more": true
  }
}
```

### Rules

- Results are returned over a **stable sort key** (a deterministic ordering, tie-broken by the
  item's stable ID) so paging is consistent and no item is skipped or duplicated when data
  changes between requests.
- `next_cursor` is present only while `has_more` is `true`; when `has_more` is `false` the client
  has reached the end and `next_cursor` is omitted or `null`.
- Cursors are opaque and are not guaranteed to remain valid indefinitely; an expired or malformed
  cursor yields a `400` problem-details response.
- `limit` is bounded by a server maximum; the response reflects the effective limit actually
  applied.

## 3. API Versioning Scheme

The API is versioned with a **major version in the URL path**: `/v{major}` (for example `/v1`).

### Rules

- The major version prefixes every route: `/v1/...`. Clients pin to a major version.
- The major version increments only for **breaking changes** (removing or renaming fields,
  changing types, changing required inputs, or altering established semantics).
- **Backward-compatible changes** (adding new endpoints, adding optional request fields, adding
  response fields) are made **within** the current major version without a version bump.
- When a major version is retired, it is deprecated with advance notice before removal; both the
  old and new major versions run in parallel during the transition window.
- The OpenAPI document is published per major version so `apps/web` can generate a typed client
  pinned to that version.

## 4. Stable ID Format

Every API resource is addressed by a **stable ID**: an immutable, opaque, string identifier that
never changes for the lifetime of the resource. Stable IDs are the sort tiebreaker for pagination
(Section 2) and the identity anchor for idempotent content upserts.

### Rules

- A stable ID is a **prefixed, URL-safe string**: a short resource-type prefix, a separator, and
  an opaque unique component — for example `usr_01HZX9…`, `qz_01HZX9…`, `qa_01HZX9…`. The prefix
  identifies the resource type; clients treat the whole value as opaque.
- Stable IDs are **immutable**: a resource keeps the same stable ID across edits and content
  syncs. Content items carry both a `stable_id` (identity) and a `content_version` hash (which
  changes when the item's content changes); the `stable_id` never changes.
- Stable IDs are **globally unique** and are **not** sequential database primary keys; internal
  numeric keys are never exposed in the API.
- Content synchronization is an **idempotent upsert keyed by the stable ID**: re-syncing the same
  item updates it in place rather than creating a duplicate (see `docs/DATA-MODEL.md` (D3),
  failure scenario 4.5).

## 5. Idempotency Keys for Mutations

Unsafe, non-idempotent mutations (notably `POST` requests that create or submit, such as quiz
submissions) support an **idempotency key** so a retried request is processed at most once.

### Request

- The client sends an `Idempotency-Key` request header whose value is a unique,
  client-generated token for the logical operation (for example a UUID).

### Rules

- The server records the idempotency key together with the result of the first successful
  processing of that operation.
- A repeat request carrying the **same idempotency key** for the **same operation** is **deduped**:
  the server does not perform the side effect again and returns the stored result of the original
  request (so retries are safe).
- Idempotency keys are retained long enough to cover client retries; the stored result is keyed by
  the idempotency key.
- A reused idempotency key sent with a **conflicting** request body is rejected with a problem
  details response so a key is never silently applied to a different operation.
- Safe, already-idempotent methods (`GET`) do not require an idempotency key.

## 6. Failure Scenario 4.6 — Duplicate Quiz Submission

**Condition:** a duplicate quiz submission is received.

**Documented behavior (normative):**

1. **An idempotency key dedupes the submission.** A quiz submission carries an `Idempotency-Key`
   (Section 5). A second submission with the same idempotency key for the same operation is
   deduped: the submission is processed at most once and the stored result of the first
   processing is returned instead of recording the attempt again.
2. **Re-answering the same question within 24 hours of the first answer yields no additional
   mastery gain.** When the learner answers the same question again within 24 hours of the first
   answer, that repeat answer produces no additional mastery gain. (The domain rule is in
   #[[file:.kiro/steering/domain-rules.md]]; the data-level enforcement is in
   `docs/DATA-MODEL.md` (D3).)
3. **The best attempt still counts for completion.** Despite deduplication and the no-additional-
   mastery window, the learner's best attempt is the one that counts toward completion.

**API surface:**

- A genuinely duplicate submission (same idempotency key) returns the original result rather than
  creating a second attempt; where the duplicate is surfaced as an error it uses RFC 9457 problem
  details (Section 1) with HTTP `409 Conflict`.
- The 24-hour no-additional-mastery window and the best-attempt-counts-for-completion rule are
  enforced consistently with the data model (`docs/DATA-MODEL.md` (D3)); the API never grants
  additional mastery for a same-question re-answer inside that 24-hour window.

## Summary of Normative Values

| Topic | Normative value |
|-------|-----------------|
| Error format | RFC 9457 problem details with `type`, `title`, `status`, `detail`, `instance` |
| Pagination | Cursor-based (keyset) over a stable sort key tie-broken by stable ID; bounded `limit` |
| Versioning | Major version in the path `/v{major}`; major bump only for breaking changes |
| Stable ID | Immutable, opaque, prefixed URL-safe string; `stable_id` identity + `content_version` hash; idempotent upsert keyed by stable ID |
| Idempotency | `Idempotency-Key` header on unsafe mutations; same key ⇒ processed at most once, stored result returned |
| Failure 4.6 | Idempotency key dedupes; re-answering the same question within **24 hours** yields no additional mastery gain; best attempt still counts for completion |
